# Little Tomato — Shopify commerce architecture research

Researched 2026-10-25 against the current official docs (Admin, Storefront and Functions API version 2026-10, "latest").

**Legend.** VERIFIED = I read it in the cited official page during this research (shopify.dev, help.shopify.com, shopify.com/legal, or the hosting provider's own docs); the URL follows. UNVERIFIED = not documented, only my inference, or something only the real store can confirm. Facts are paraphrased, not quoted.

**Method / safety.** Shopify docs search tool (read-only) plus the raw markdown of the cited pages. No Shopify account or store was created, no store-data tool and no mutation was called, nothing in the project was edited.

---

## 0. Bottom line

1. **A self-built ("custom") app cannot run a Shopify Function on a non-Plus store.** Functions in a *public* App Store app work on every plan; Functions in a *custom* app need Shopify Plus. So the "supported server-side enforcement" tool (Cart Transform / Cart and Checkout Validation) is only reachable without Plus by publishing a public (listed or unlisted) app that passes Shopify app review, or by installing someone else's public app.
2. **The current component cart cannot be enforced, whatever the front end does.** The Storefront API accepts cart writes without any token, and the public token is visible to buyers, so anyone can build a cart with any lines, quantities and attributes and skip the site entirely. Attributes are buyer-supplied text.
3. **Enforcement therefore has to come from one of two places:** (a) a Function that validates the cart at checkout (works even if the buyer bypasses the site), or (b) making the component variants unbuyable through the storefront and creating the order only from a server that holds an Admin token (draft order).
4. **Recommended: Option B** — a tiny Cloudflare Worker (free tier, artist-owned) that re-validates the design, builds a **draft order from real variant lines at catalog prices**, and returns the draft's checkout link; component variants are un-published from storefront channels; Shopify Flow audits every paid order. Upgrade path to Functions if the shop later moves to Plus or ships a public app.
5. **Biggest unknowns need the real store** (section 5): can an API-created draft contain un-published variants, does the invoice link work without emailing it, and does the draft checkout collect email and shipping the way the docs imply.

## 1. Answers with citations

### Q1. Cart Transform Functions

- Operations are `lineExpand` (one line becomes its component lines), `linesMerge` (several lines become one bundle line under a parent variant, with an optional price adjustment) and `lineUpdate` (override price, title, image). Older names were expand / merge / update. **VERIFIED** https://shopify.dev/docs/api/functions/latest/cart-transform , https://shopify.dev/changelog/posts/standardized-target-and-operation-names-across-function-apis
- **Who can run Functions:** stores on any plan can use *public* apps (App Store distributed) that contain Functions; only Plus stores can use *custom* apps that contain Function APIs. **VERIFIED** https://shopify.dev/docs/apps/build/functions , https://shopify.dev/docs/api/functions/latest (section "API availability"). Shopify's own plan table agrees: public apps with Functions = Basic or higher and Plus; custom apps with Functions = Plus only. **VERIFIED** https://help.shopify.com/en/manual/checkout-settings/checkout-customization
- **Custom app on a non-Plus store: not supported for Functions.** Custom distribution installs on one store (or stores in one Plus organization) and needs no approval; public distribution needs Shopify approval. **VERIFIED** https://shopify.dev/docs/apps/launch/distribution . Development stores can be used for building and testing. **VERIFIED** https://shopify.dev/docs/api/functions/latest/cart-transform (note on `lineUpdate`) and https://shopify.dev/docs/apps/build/functions/test-debug-functions
- **"Unlisted" is a public-app flavour, not a custom app:** public apps are either listed or unlisted, both go through Shopify's app review, and an unlisted app is installed from a link and is not shown in search or categories. **VERIFIED** https://help.shopify.com/en/manual/apps/app-types/custom-apps . Visibility can be limited in the Partner Dashboard. **VERIFIED** https://shopify.dev/docs/apps/launch/distribution/visibility . Whether Shopify will approve a public app that exists for one small shop: **UNVERIFIED** (App Store requirements were skimmed, none seen that forbids it; review is at Shopify's discretion: https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements).
- `lineUpdate` (price/title/image override) is limited to development stores or Plus. The page contradicts itself: one note says "development stores or Plus", another says "Plus" only; the Bundles help page adds that it is not available on Plus *trial* stores. Treat as Plus-only in production. **VERIFIED** https://shopify.dev/docs/api/functions/latest/cart-transform , https://help.shopify.com/en/manual/products/bundles/eligibility-and-considerations
- Per-component prices, titles and images inside `lineExpand` have "feature not available for the given shop" error codes, so they are gated somehow; which plans is not stated. **UNVERIFIED** (error table at the cart-transform URL above). `linesMerge` lists no such gating errors. **VERIFIED** (absence in the same error table).
- Merge price rule: final price = sum of component prices plus the adjustment, if any. **VERIFIED** (cart-transform URL, "Pricing adjustments").
- **Limits.** One cart transform function per app per store; `lineExpand` max 150 expanded items; merged/expanded quantity max 2,000. **VERIFIED** (cart-transform URL). Resource limits for carts up to 200 lines: input 128 kB, output 20 kB, 11 million instructions; compiled binary 256 kB; input query max 3,000 bytes and query cost 30; scales proportionally above 200 lines. **VERIFIED** https://shopify.dev/docs/api/functions/latest . No separate cap on the number or size of line attributes is documented beyond the input size. **UNVERIFIED**.
- **Can it read the design?** Yes: the input query can read a per-line attribute with `attribute(key: ...)`. Shopify's own example reads a line attribute named "Assembly Service Added" and expands the line to add an assembly-service variant. **VERIFIED** (cart-transform URL, example "Create a cart bundle with an add-on").
- **Can it reject the cart?** No. Its output is only the three operations. Blocking checkout is the validation API's job. **VERIFIED** (cart-transform URL operation list; https://shopify.dev/docs/api/functions/latest/cart-and-checkout-validation). What happens if a cart-transform function throws is not documented. **UNVERIFIED**.
- **Where it runs:** Storefront API carts, Draft Order (Admin and Checkout), accelerated checkout: supported. Create Order API, Order Edit, pre-order, subscriptions: not supported. Lines with a selling plan are rejected. **VERIFIED** (cart-transform URL, compatibility list); Storefront Cart API executes Validation and Cart Transform functions. **VERIFIED** https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/migrate-to-cart-api

### Q2. Cart and Checkout Validation Functions

- Validation functions run on Shopify's servers, can block checkout progress, cover online-store carts, carts built for custom storefronts, and the checkout (express checkouts included), and are described as not bypassable by customers. **VERIFIED** https://shopify.dev/docs/apps/build/checkout/cart-checkout-validation , https://shopify.dev/docs/api/functions/latest/cart-and-checkout-validation
- **Plan availability:** no validation-specific plan limit on the API page; the general Functions rule applies (public app any plan, custom app Plus). A non-developer route exists: install a third-party validation app from the App Store. **VERIFIED** https://help.shopify.com/en/manual/checkout-settings/checkout-customization
- **Can it check a bundle's lines against its declared design?** The input exposes cart lines with quantities and `attribute(key:)`, so a function can parse the "Design" attribute and compare it with the component lines (one assembly, one tomato, strand count, bead counts, one clasp). **VERIFIED** (field list at the validation API URL above); the exact logic fitting inside the instruction budget is **UNVERIFIED** (very likely, not measured).
- Errors appear on the Storefront API `Cart` object, in themes using the cart template, and in checkout. **VERIFIED** (validation API URL). Whether a failing validation also rejects the Storefront `cartCreate` call itself is not stated. **UNVERIFIED**.
- **Fail-open default:** a validation's `blockOnFailure` defaults to false, meaning a function that crashes or times out does not block checkout unless it is set true at creation. **VERIFIED** https://shopify.dev/docs/api/admin-graphql/latest/input-objects/ValidationCreateInput . Max 25 active validation functions per store. **VERIFIED** (validation API URL).
- Validation also covers draft-order checkouts; a merchant can tick "ignore checkout rules" on a draft before sending it. **VERIFIED** https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/create-draft , https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/send-draft
- Shopify's free "Checkout Blocks" app does not do this: its listing describes thank-you-page content, order-value limits and address rules, with fuller checkout options on Plus. **VERIFIED** https://apps.shopify.com/checkout-blocks

### Q3. Shopify Bundles app and component inventory

- Shopify Bundles is a free first-party app on all plans; it makes fixed bundles and multipacks, **not** mix-and-match. Mix-and-match = a third-party public bundle app, or a Plus store building with the Bundles APIs. **VERIFIED** https://help.shopify.com/en/manual/products/bundles/shopify-bundles , https://help.shopify.com/en/manual/products/bundles/eligibility-and-considerations
- Limits: fixed bundles up to 30 components, "dynamic" bundles up to 150, up to 2,000 units per component, up to 3 options, no nested bundles, not with selling plans or custom (draft) items. **VERIFIED** (the two help pages above) and https://shopify.dev/docs/apps/build/product-merchandising/bundles/add-product-fixed-bundle
- Bundles can be sold on custom/headless storefronts if bundle publishing is on; the Storefront API supports fixed and customized bundles. Stores must use an upgraded checkout (no `checkout.liquid`). **VERIFIED** https://shopify.dev/docs/apps/build/product-merchandising/bundles , https://help.shopify.com/en/manual/products/bundles/eligibility-and-considerations
- **Inventory.** A fixed bundle's available quantity is the lowest whole-bundle count any tracked component allows; untracked or "continue selling" components are ignored. **VERIFIED** (eligibility page). Orders store the *components* as lines with a reference to the parent; SKUs are listed per component. **VERIFIED** https://shopify.dev/docs/apps/build/product-merchandising/bundles/start-building , https://help.shopify.com/en/manual/products/bundles/shopify-bundles . Shopify decrements available inventory for tracked variants in an order. **VERIFIED** https://shopify.dev/docs/apps/build/orders-fulfillment/inventory-management-apps . **No page I read states in one sentence that selling a bundle decrements each component**; it follows from the two facts above. **UNVERIFIED** (inference; test it).
- For Function-built ("customized") bundles, Shopify re-checks components in cart and checkout, but the app has to keep the parent's in/out-of-stock state on the storefront. **VERIFIED** (start-building page).
- **Fit for Little Tomato:** a fixed bundle cannot model the custom charm. Ordered bead choices alone give about 5.7e20 strand combinations (24 colour-shape types, 3 to 5 beads, 1 to 3 strands), times 4 tomatoes and 5 clasp keys (20 pairs), about 1e22 designs; the bundle limits are 30 components and 3 options. **UNVERIFIED** (my arithmetic against the verified limits). It *is* a good fit for the **3 ready-made designs** (each is 1 tomato + 1 clasp + at most 15 bead variants + assembly, under 30 components), which would fix the ready-made versus raw-stock accounting gap listed in SHOPIFY_SETUP.md. **UNVERIFIED** (my analysis).

### Q4. Draft Orders API as the enforcement point

- `draftOrderCreate` takes line items by `variantId` with `quantity` and `customAttributes` (custom items use a title and price instead), plus customer, addresses, shipping line and tags. Scope: `write_draft_orders`, which carries no "Shopify approval required" marker. **VERIFIED** https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderCreate , https://shopify.dev/docs/api/admin-graphql/latest/input-objects/DraftOrderLineItemInput , https://shopify.dev/docs/api/usage/access-scopes
- **Price source.** A variant line uses the catalog price unless a `priceOverride` is supplied; custom items carry their own price. Variant lines keep inventory tracking; custom items represent things "not in inventory". **VERIFIED** (DraftOrderLineItemInput and draftOrderCreate pages above). Choose variant lines with no override.
- **Customer payment.** `DraftOrder.invoiceUrl` is the checkout link normally sent in the invoice email; on that checkout the customer enters billing details, selects a shipping method and pays, and the draft becomes an order marked Paid. **VERIFIED** https://shopify.dev/docs/api/admin-graphql/latest/objects/DraftOrder , https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/send-draft . Using `invoiceUrl` *without* sending the email, as a plain redirect: **UNVERIFIED** (the help page describes a "Share checkout link" path for staff; the API field is documented only as the link in the invoice email).
- **Price lock.** When a staff member sends an invoice or shares a link, product pricing is locked by default; unlocking is an explicit toggle. **VERIFIED** (send-draft and create-draft help pages). That the same lock applies to an API-created draft's `invoiceUrl`: **UNVERIFIED**.
- **Tax and shipping.** Taxes are included by default from store tax settings and the shipping (else billing) address; you can set a preset, custom, local-delivery or pickup shipping option; delivery-method customizations apply to draft checkouts. **VERIFIED** https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/create-draft . If a shipping line is omitted, which rates the invoice checkout offers: **UNVERIFIED** (help says the customer "selects a shipping method"; not tested for API drafts).
- **Inventory.** By default a draft does **not** reserve stock; `reserveInventoryUntil` reserves it and makes the units `committed` until the reserve expires (then automatically restocked); without a reserve, an item that has sold out makes the customer's checkout stop with an out-of-stock notice; completing the draft commits inventory. **VERIFIED** https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderCreate , https://shopify.dev/docs/api/admin-graphql/latest/mutations/draftOrderComplete , https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/send-draft , https://shopify.dev/docs/apps/build/orders-fulfillment/inventory-management-apps . Reserving requires inventory tracking on the item. **VERIFIED** (create-draft help page).
- **Abandoned drafts.** Drafts created on or after 2025-04-01 are deleted automatically after one year of inactivity (any edit resets the timer); `draftOrderDelete` removes one earlier. **VERIFIED** https://shopify.dev/docs/api/admin-graphql/latest/objects/DraftOrder , https://help.shopify.com/en/manual/fulfillment/managing-orders/create-orders/create-draft . I found no shorter automatic expiry. **UNVERIFIED** (absence).
- **Plan availability.** No draft-order plan matrix found. Shopify's B2B plan table lists "Draft order to invoice" for Basic, Grow, Advanced and Plus. **VERIFIED** https://help.shopify.com/en/manual/b2b/getting-started/plan-features . Starter and Retail: **UNVERIFIED**. Custom apps are created in the Dev Dashboard; no plan restriction on the Admin API itself was found, and Admin API limits scale by plan (Standard 100 points/s, a single query max 1,000 points). **VERIFIED** https://help.shopify.com/en/manual/apps/app-types/custom-apps , https://shopify.dev/docs/apps/build/apis/graphql-admin/rate-limits
- **Admin token reality in 2026.** New admin-created custom apps (the static "shpat_" token tutorials) can no longer be created; use a Dev Dashboard app. For a server acting on your own store, the client-credentials grant returns a token that expires after 24 hours, so the server must refresh it, and it only works when the app and the store are in the same Shopify organization. **VERIFIED** https://shopify.dev/docs/apps/build/authentication-authorization/legacy/admin-custom-apps , https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant . Store owners can create custom apps; staff need the App development > Develop permission; collaborators cannot reach the Dev Dashboard. **VERIFIED** https://help.shopify.com/en/manual/apps/app-types/custom-apps
- **Bundles and drafts.** Draft orders may default to an older checkout version that does not support bundles. **VERIFIED** (bundles eligibility page). Cart Transform and Validation functions do run on draft orders. **VERIFIED** (compatibility lists on both Function API pages).
- **Rule against using drafts as a general checkout:** I found none. The developer terms say to use Shopify Checkout for payments and not divert to another checkout; an invoice checkout *is* Shopify Checkout. **VERIFIED** https://www.shopify.com/legal/api-terms (last updated 2026-10-07). Drafts are described as orders a merchant creates on a customer's behalf; automated storefront use is neither described nor forbidden, and Shopify says it may restrict scopes for apps without a legitimate use for the data. **VERIFIED** (DraftOrder page). One clause reads oddly: the terms also say not to use Shopify Checkout other than as a "Pop-up Implementation", defined as payment opening in a separate window, while Shopify's own headless docs tell developers to redirect buyers to `checkoutUrl`. **UNVERIFIED** how Shopify applies it (docs and terms point different ways); applies equally to the current Storefront-cart design.

### Q5. Storefront API cart: tampering, signed properties, limits, token scoping

- Cart read/write works **tokenless**; the *public* access token is for browsers and apps "where the token is visible to buyers"; created with `storefrontAccessTokenCreate`; max 100 active storefront tokens per app per shop. **VERIFIED** https://shopify.dev/docs/api/storefront
- Therefore line attributes are whatever the caller sends: any visitor can call `cartCreate` / `cartLinesAdd` directly with any variants, quantities and attribute text. **VERIFIED** (premise above); the conclusion is my inference. **UNVERIFIED** only in the sense of not being tested against a real store.
- **Signed or verified properties:** I found none in the Storefront cart docs, the Functions docs, or the Checkout UI docs (extensions can *change* line attributes, which shows they are mutable data). **UNVERIFIED** (absence of a feature across a search, not proof).
- Cart ID is `token?key=secret`; the key is needed to modify a cart and must not be exposed. The documented sample `checkoutUrl` shows only the token, not the key, so whether a buyer can derive the key from `checkoutUrl` is unclear. **VERIFIED** https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage ; the unclear point is **UNVERIFIED** (test). It does not matter for the buyer who simply builds their own cart.
- **Rate limits.** No fixed request limit for real buyer traffic (capacity scales with buyers, by IP); bots and crawlers are limited; checkout creation is throttled per minute (a `200 Throttled` error); tokenless queries have a complexity cap of 1,000; malicious-looking requests get a 430. **VERIFIED** https://shopify.dev/docs/api/storefront . A cart holds at most 500 lines, abandoned carts expire within 30 days, and input arrays are capped at 250 values. **VERIFIED** https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart , https://shopify.dev/docs/api/storefront/latest/input-objects/CartLineInput
- **Token scoping.** Storefront permissions are the `unauthenticated_*` scopes (for example product listings, product inventory, checkouts/cart); the Headless channel manages them in the admin. A **private** token (server-side, header `Shopify-Storefront-Private-Token`, plus `Shopify-Storefront-Buyer-IP` for buyer traffic) is the secret variant. **VERIFIED** https://shopify.dev/docs/api/usage/access-scopes , https://shopify.dev/docs/api/storefront
- Storefront API terms note: you cannot use it to duplicate existing Shopify functionality. **VERIFIED** (storefront page, "Usage limitations").
- Buyers only see what is published: publishing controls which products and variants are visible on a channel or catalog, and only products published in every applicable catalog can be bought; variants can be published or unpublished independently since API 2026-07. **VERIFIED** https://shopify.dev/docs/apps/build/sales-channels/product-publishing , https://shopify.dev/docs/apps/build/markets/build-catalog . Whether an Admin-API draft order can include a variant that is **not** published to any channel: **UNVERIFIED** (the whole bypass-proofing of Option B depends on it; test first).

- **Shopify Flow** is a free app on Basic, Grow, Advanced and Plus; the "Order created" trigger fires for customer orders and for draft orders converted to orders; the Run code action executes JavaScript on workflow data (no imports, no network, no random/clock); Send HTTP request needs Grow or higher; actions include add order tags, hold fulfillment, cancel order and send internal email. **VERIFIED** https://help.shopify.com/en/manual/shopify-flow , https://help.shopify.com/en/manual/shopify-flow/reference/triggers/order-created , https://help.shopify.com/en/manual/shopify-flow/reference/actions/run-code , https://help.shopify.com/en/manual/shopify-flow/reference/actions
- Whether Flow's order data exposes line-item custom attributes to Run code: **UNVERIFIED** (the trigger exposes the Admin API Order object; test).
- **Webhooks** (`orders/create`, `orders/paid`, `draft_orders/*`): subscribe in app config, verify the HMAC signature, de-duplicate with `X-Shopify-Webhook-Id`, and expect missed or out-of-order deliveries, so reconcile with periodic API reads. Payloads carry `line_items[].properties` and `line_item_groups`. **VERIFIED** https://shopify.dev/docs/apps/build/webhooks , https://shopify.dev/docs/api/webhooks . That `orders/create` fires when a draft order's invoice is paid: **UNVERIFIED** (Flow's trigger says so; the webhook page does not).
- **Customer data.** Developer docs say custom apps always get Level 1 and Level 2 protected customer data; the help centre says Custom Level 2 PII apps need the Grow plan or higher. These two statements disagree or apply to different custom-app types. **VERIFIED** (both pages) https://shopify.dev/docs/apps/launch/protected-customer-data , https://help.shopify.com/en/manual/apps/app-types/custom-apps ; which applies to a Dev Dashboard app on Basic: **UNVERIFIED**. A composition audit does not need names or addresses; filter the payload fields. **VERIFIED** that field filtering exists (https://shopify.dev/docs/apps/build/webhooks, "Delivery filtering").

## 3. (b) Recommendation: Option B, with Flow as the safety net

**Why.** It is the only option that gives real server-side control of composition and price without Plus, without an app-store review, and without recurring cost, and the artist can own every piece. It reuses the existing, tested design rules (`validDesign`, `components`, `priceDesign`) on the server instead of trusting the browser. Functions (Option C) are the more native fit, so keep them as the upgrade path, but they need either Plus or a public app that Shopify must approve.

**Why not simply harden the cart.** Cart writes are tokenless and the public token is visible to buyers, so any amount of front-end checking leaves the Storefront API open to hand-built carts (Q5). Without a Function, the lever is to make the component variants unbuyable there.

**Step list**

1. **Confirm the store first** (section 5, items 1 to 4): plan tier, Dev Dashboard availability for the artist's login, and that an API-created draft can contain a variant that is not published to any channel. If the last one fails, switch to the fallback in step 11.
2. **Catalog.** Keep the catalog keys (the code emits 38, checked with `catalogEntries()`: 5 clasp keys incl. `clasp-dust-usbc` and `clasp-dust-lightning`; SHOPIFY_SETUP.md says 37, a small doc mismatch to fix). Component variants (assembly, strand, tomatoes, clasps, beads) stay active but are un-published from the Online Store/Headless publications (variant-level publishing exists since API 2026-07). The 3 ready-made products stay published. Optional: model each ready-made as a fixed bundle with the free Bundles app so raw stock is deducted.
3. **App.** The artist (store owner) creates a custom app in the Dev Dashboard under her own organization, scopes `read_products` and `write_draft_orders` (add `read_draft_orders` for the cleanup job), installs it on the store. Client ID and secret go into Cloudflare Worker secrets only, never into `dist/`.
4. **Worker.** One file, three routes. `GET /prices`: read variant prices and availability with the Admin API, cache for about a minute (this replaces the browser's Storefront price query for components). `POST /checkout`: input is the bag (designs and ready-made ids) and contact email only; re-run the shared validation and `components()` logic, map keys to variant GIDs from a server-side table, create the draft with variant lines, no `priceOverride`, `customAttributes` carrying Charm group, Design and Component, tag `web`, optionally an HMAC of the design in an attribute for later audit; return `invoiceUrl`, subtotal and currency. Cron job: delete open drafts tagged `web` older than N days with `draftOrderDelete`. Token: request via client credentials, cache until near expiry.
5. **Front end.** Replace `createCheckout` for custom bags with a POST to the Worker. Compare the returned subtotal and currency with the on-screen total as today, refuse a non-HTTPS URL, then redirect to `invoiceUrl`. Keep the mixed-bag path by sending ready-mades through the same draft.
6. **Abuse controls.** CORS allow-list limited to the site's domain, Cloudflare Turnstile on the checkout button, body-size and bag-size caps (reuse `sanitizeCart` limits), per-IP throttle. Do not reserve inventory at first (a short reserve invites stock-locking abuse); the checkout's own out-of-stock stop covers races.
7. **Audit layer.** Shopify Flow "Order created" workflow: Run code compares line quantities with the Design attribute; on mismatch add tag `needs-review`, hold fulfilment, send an internal email to the artist. If Flow cannot read line attributes (item 6 in section 5), use an `orders/create` webhook handled by the same Worker with HMAC verification and a nightly reconciliation read.
8. **Dev store rehearsal.** Run steps 2 to 7 on a development store: max design (3 strands x 5 beads), quantity 2, mixed ready-made plus custom, sold-out component, price change mid-checkout, cancelled checkout, test-mode payment.
9. **Docs.** Update `SHOPIFY_SETUP.md` (Admin token lives only in the Worker; component variants unpublished; Flow audit) and the acceptance checklist; remove the "not server-enforced" caveat only after step 8 passes.
10. **Go live** on the artist's real store only after section 5 items are checked there.
11. **Fallback if drafts cannot hold un-published variants:** keep the component variants published, price the tomato as "tomato with assembly" so the cheapest purchasable part is never below cost, keep Flow audit and artist review before making anything, and plan Option C or Plus.
12. **Upgrade path.** If the shop moves to Plus, or the artist is willing to pass app review, add a Validation function (and optionally Cart Transform merge) so the standard Storefront cart is also safe; Option B's Worker can then be retired.

## 4. Known conflicts and soft spots in the docs

- Cart Transform page: "development stores or Plus" versus "Plus" for the update operation.
- Protected customer data for custom apps: developer docs say always available; help centre says Level 2 needs Grow or higher.
- Developer terms: the "Pop-up Implementation" clause versus Shopify's instruction to redirect to `checkoutUrl`.
- Bundles help says Plus can "build a custom bundle offering"; the Functions pages say public apps on any plan can contain Functions. These agree once you read the first as "build your own".
- No page gives a draft-order plan matrix; the B2B table is the only plan evidence.

## 5. (c) Facts only the real store can confirm

1. **Plan tier** (Basic, Grow, Advanced, Plus, Starter/other). Drives Flow's HTTP action, Admin API rate bucket (100 points/s on standard plans), and whether Functions in a custom app are possible at all.
2. **Dev Dashboard access** for the artist's login: can she create a custom app in her own organization and install it on her store? Does client credentials succeed (it fails with `shop_not_permitted` if app and store are in different organizations)?
3. **Draft order with an un-published variant**: does `draftOrderCreate` accept a variant that is not published to any channel, and does the invoice checkout let it be bought? This decides whether Option B is bypass-proof.
4. **`invoiceUrl` as a plain redirect**: usable immediately after creation, without `draftOrderInvoiceSend`? Does it expire? Is price lock on for an API-created draft?
5. **Draft checkout contents**: does the page collect email, shipping address and shipping method when the draft was created with only line items and an email? Which shipping rates appear for a draft without a `shippingLine`? Are Shop Pay and Apple Pay available there?
6. **Flow data**: does Flow's Order created object expose `lineItems.customAttributes` to Run code, and does Run code have the arithmetic needed? Does the trigger fire on paid drafts (the docs say yes)?
7. **Webhook behaviour** if a Worker handler is used: does `orders/create` fire for a paid draft, and are `line_items[].properties` populated with the draft's custom attributes?
8. **Inventory**: sell a draft containing component variants and confirm each tracked component decrements once; confirm an untracked assembly-labour variant causes no stock error; confirm the out-of-stock stop when one bead is at zero and nothing is charged.
9. **Line limits** on a draft order (the current bag can reach 20 designs of up to 19 lines each) and on `draftOrderCreate` latency under the Worker's 10 ms CPU budget (network waits do not count).
10. **Storefront bypass test**: with the component variants un-published, can a hand-built `cartCreate` still buy them? Does the public token still read ready-made products and prices?
11. **Cart key exposure** (only if the cart route is kept): does `checkoutUrl` reveal the cart key so a buyer can edit lines afterward?
12. **Protected customer data**: does a Dev Dashboard custom app on this plan receive order webhooks and customer fields, or are they redacted (the two docs disagree)?
13. **Function route (only if Option C is pursued):** whether Shopify will review and approve a public app for one shop; how a Function-only app activates `cartTransformCreate` / `validationCreate` without a backend; whether a failing cart transform fails open or closed; whether per-component price overrides and `lineExpand` titles/images are allowed on this plan.
14. **Tax and shipping setup**: the tax category of the assembly-labour line, shipping profile weights for physical components, and the production-time promise published at checkout (Shopify Payments reviews fulfilment against promises).
15. **Currency and market context**: a draft's currency and prices follow the customer's market; confirm single-currency behaviour matches the front end's check.
